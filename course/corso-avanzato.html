Design · Variabili e token

Dalle variabili Figma ai token in codice

Leggi le variabili del frame selezionato con get_variable_defs.
Esporta tutte le collezioni e i modi (light/dark, brand A/B)
in formato W3C Design Tokens (JSON).
Poi genera tokens.css con custom properties per ogni modo.
Mantieni i nomi gerarchici (color/primary/500 -> --color-primary-500).
Segnala valori hardcoded che non puntano a una variabile.
Attenzione

Sviluppo · Hook

Un hook che formatta dopo ogni modifica

// .claude/settings.json (versionato nel repo)
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "npx prettier --write \"$(jq -r '.tool_input.file_path')\"" }
        ]
      }
    ]
  }
}

L’hook riceve il JSON dell’evento su stdin. In un hook PreToolUse, exit code 2 blocca la chiamata e lo stderr diventa il motivo che Claude legge: utile per vietare rm o la lettura di .env.

Sviluppo · Permessi

Allowlist e modalità di permesso

{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Bash(npm run lint)", "Edit(src/**)"],
    "ask":   ["Bash(git push:*)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)", "Bash(curl:*)"]
  }
}

Ordine di valutazione: deny, poi ask, poi allow. Modalità (Shift+Tab o --permission-mode): default, acceptEdits, plan, bypassPermissions (solo in container isolati). Regole condivise in .claude/settings.json, personali in settings.local.json.

Slash command o Skill?

  • Accetta argomenti ($ARGUMENTS)
  • Ideale per rituali ripetuti
Skill

  • Contesto caricato solo quando serve
  • Ideale per know-how: brand, design system

Sviluppo · Test

Test prima, codice dopo

  1. Scrivi i test

    “Scrivi test per il form di contatto, niente implementazione.” Verifica che falliscano.

  2. Committa i test

    Così Claude non può “aggiustarli” per farli passare.

  3. Implementa e itera

    “Fai passare i test senza modificarli.” Claude esegue, legge l’errore, corregge.

  4. Verifica indipendente

    Un subagent o una seconda sessione rilegge il diff cercando overfitting.

Sviluppo · MCP

MCP: come funziona e dove si configura

Il protocollo
  • Un server MCP espone tools (azioni), resources (dati) e prompts (modelli riusabili).
  • Trasporti: stdio (processo locale) e Streamable HTTP (remoto, spesso con OAuth).
  • Messaggi JSON-RPC 2.0 tra client e server (⚠ da verificare).
Scope in Claude Code
  • local (default): solo voi, solo questo progetto.
  • project: .mcp.json versionato, approvazione richiesta.
  • user: tutti i vostri progetti.

Nel .mcp.json condiviso scrivete "Bearer ${GITHUB_PAT}": il token resta nell’ambiente di ciascuno, fuori dal repo.

// npm install @modelcontextprotocol/server zod   (SDK TypeScript v2)
import { McpServer } from '@modelcontextprotocol/server';
import { StdioServerTransport } from '@modelcontextprotocol/server/stdio';
import * as z from 'zod/v4';

const server = new McpServer({ name: 'agenzia-tools', version: '1.0.0' });
server.registerTool('stato_progetto',
  { description: 'Stato di un progetto cliente', inputSchema: z.object({ slug: z.string() }) },
